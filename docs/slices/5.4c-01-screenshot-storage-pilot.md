# Slice 5.4c-01 — screenshot and Supabase Storage pilot

Status: **implementation and capture validation in progress**

## Goal

Test whether Tessli can capture representative public homepage previews, resize
and compress them into consistent card media, store them on Tessli-controlled
Supabase Storage, and serve them without depending on the source website at
runtime.

This is a five-resource feasibility pilot. It does not authorize a full-catalogue
capture run or publish the pilot screenshots into production catalogue media.

## Pilot resources

| Resource ID | Resource | Reason included |
| --- | --- | --- |
| `resource-fd3c2a3a5685` | Figma | Metadata discovery exceeded the bounded HTML limit; tests a complex public homepage. |
| `resource-25d0d0a31e39` | Webstudio | Tests a visually rich builder homepage and a previously heavy preview. |
| `resource-66b5da3637f8` | Uizard | Tests a product homepage whose official preview exceeded the preferred payload. |
| `resource-29300a9360ac` | Locofy | Tests a resource that previously had only a usable favicon. |
| `resource-21359fe8c171` | Webflow | Provides a strong comparison case with existing representative official media. |

## Capture and compression contract

- source URLs are fixed in the pilot script and use HTTPS;
- browser viewport: **1440 × 756**;
- output: **960 × 504 WebP**;
- target aspect ratio: **40:21**;
- maximum stored object size: **300 KiB**;
- compression begins at quality 78 and steps down only when required;
- screenshots use reduced motion, a bounded virtual-time budget, and a hard
  process timeout;
- one failed website does not hide the results for other pilot resources;
- raw and optimized screenshots remain GitHub Actions review artifacts, not
  repository binaries.

## Supabase Storage contract

- project: existing dedicated `tessli` project;
- public bucket: `resource-previews`;
- allowed MIME type: `image/webp` only;
- bucket file-size ceiling: **307,200 bytes**;
- pilot object names are stable: `pilot/<resource-id>.webp`;
- public read is intentional because these are public catalogue covers;
- direct anonymous Storage insert policy was removed before capture;
- a temporary Edge Function accepts only the five exact resource IDs, validates
  payload size and WebP magic bytes, refuses overwrite, and uploads using
  server-side credentials;
- the temporary uploader must be closed after the capture run.

No Supabase secret, service-role key, database password, or upload credential is
stored in GitHub. The public project and bucket URLs are not credentials.

## Acceptance criteria

- [ ] at least one representative site captures successfully;
- [ ] successful outputs are exactly 960 × 504 WebP;
- [ ] every uploaded object is at or below 307,200 bytes;
- [ ] manifest records raw size, optimized size, compression percentage,
      quality, SHA-256, object URL, and failures;
- [ ] optimized files are uploaded to the existing Tessli Supabase project;
- [ ] every public object URL is readable after upload;
- [ ] contact-sheet review identifies consent walls, blank states, loading
      skeletons, unrelated content, or poor crops;
- [ ] normal application build and tests remain network-free;
- [ ] `lib_data/resource-media.json`, coverage, and generated catalogue remain
      unchanged;
- [ ] temporary upload capability is closed after the run;
- [ ] Supabase security advisors are checked after the storage migration.

## Exclusions

- no capture for the other 290 resources;
- no anti-bot, authentication, paywall, consent, or access-control bypass;
- no automatic production approval;
- no overwrite of an existing pilot object;
- no database table for image bytes;
- no runtime screenshot endpoint in the Tessli application;
- no arbitrary URL input, proxy, wildcard fetcher, or unrestricted upload path;
- no card layout, auth provider, user-data, catalogue fact, or unrelated UI work.

## Review boundary

Successful upload proves the mechanics, not visual suitability. A human must
review the optimized contact sheet before any pilot URL is copied into
`lib_data/resource-media.json`. The broader screenshot slice begins only after
the pilot establishes acceptable capture quality, compression, storage delivery,
and failure handling.

## Rollback

Before production media uses this bucket, rollback consists of closing the pilot
uploader, deleting the five `pilot/` objects, and deleting the bucket if it is
empty. The applied migration history remains part of the project audit trail; a
forward migration is required for any future bucket-policy change.
