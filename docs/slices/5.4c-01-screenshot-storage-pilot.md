# Slice 5.4c-01 — screenshot and Supabase Storage pilot

Status: **pilot complete — production publication intentionally deferred**

## Goal

Test whether Tessli can capture representative public homepage previews, resize
and compress them into consistent card media, store them on Tessli-controlled
Supabase Storage, and serve them without depending on source websites at
runtime.

This was a five-resource feasibility pilot. It does not authorize a full-
catalogue capture run or publish pilot screenshots into production catalogue
media.

| Resource ID | Resource | Reason included |

## Capture contract

- fixed HTTPS source URLs;
- browser viewport: **1440 × 756**;
- output: **960 × 504 WebP**;
- target aspect ratio: **40:21**;
- maximum stored object size: **307,200 bytes**;
- compression begins at quality 78 and steps down only when required;
- reduced motion, bounded virtual time, and a hard process timeout;
- one failed site does not hide other pilot results;
- raw and optimized images remain workflow review artifacts, not Git binaries.

## Supabase Storage result

The existing Tessli project now contains the public `resource-previews` bucket.

- allowed MIME type: `image/webp` only;
- file-size ceiling: **307,200 bytes**;
- stable pilot paths: `pilot/<resource-id>.webp`;
- stored objects: **5**;
- stored total: **125,610 bytes**;
- cache control: `max-age=31536000`;
- direct `storage.objects` insert policies after setup: **0**;
- overwrite is refused rather than silently replacing reviewed media.

The first migration created the constrained bucket and a temporary exact-path
insert policy. The immediately following migration removed that policy before
capture. Uploads then passed through a temporary Edge Function restricted to the
five exact pilot IDs, WebP magic bytes, and the size ceiling.

After the final capture run, the Edge Function was redeployed as version 2 with
JWT verification enabled and a closed `410` implementation. The temporary
capture workflow was removed from the final repository diff.

No Supabase secret, service-role key, database password, or upload credential is
stored in GitHub.

## Product decision

The storage and compression plan is approved as technically viable. The full-
catalogue screenshot implementation must not scale the current blind Chrome
command unchanged.

The next screenshot slice should use Playwright or a reviewed Chrome DevTools
Protocol client and support this bounded interaction sequence:

1. load the public page within strict limits;
2. identify visible consent or campaign overlays;
3. prefer **Reject all**, **Only necessary**, **Close**, or an equivalent non-
   consenting action;
4. never accept tracking merely to obtain a screenshot;
5. recapture and compare before and after states;
6. reject any page whose obstruction cannot be safely removed;
7. publish only after contact-sheet approval.

## Exclusions preserved

- no capture for the other 290 resources;
- no anti-bot, authentication, paywall, consent, or access-control bypass;
- no automatic production approval;
- no arbitrary URL input, proxy, wildcard fetcher, or runtime screenshot API;
- no database table for image bytes;
- no card layout, auth provider, user-data, catalogue fact, or unrelated UI
  change.

## Rollback

Before production media uses this bucket, rollback consists of leaving the
uploader closed, deleting the five `pilot/` objects, and deleting the bucket if
it is empty. Applied migration history remains part of the project audit trail;
future bucket-policy changes require a forward migration.
