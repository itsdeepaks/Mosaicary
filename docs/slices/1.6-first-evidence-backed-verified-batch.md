# Product Plan v2 — Slice 1.6 First Evidence-Backed Verified Batch

Status: **IN PROGRESS**

Base: `main` at `b053a99a62dc8bc21970d3317be7a36174ce755d`

## Goal

Run the Slice 1.5 human-operator workflow against the first small, independently reviewable set of Profiled sources and promote only records that satisfy every schema and semantic gate.

This slice begins the operator work. It does not treat a drafted record, repository profile, available website, passing schema, or prior evidence date as proof that a source is currently Verified.

## Bounded candidate set

The first batch is limited to exactly three candidates:

| Candidate | Why it belongs in the first batch | Required boundary |
| --- | --- | --- |
| `google-fonts` | Exercises official product/documentation claims and a documented HTTP API that requires a user-owned key. | The key may be used manually by the operator but must never enter a record, command history committed to the repository, log, fixture, or screenshot. |
| `radix-ui` | Exercises an open-source component source with strong official accessibility and package documentation but no recorded agent interface. | Package and documentation claims, current licence/terms, attribution, redistribution, and limitations must be reviewed directly. |
| `react-aria` | Exercises an open-source framework source with accessibility, interaction, and internationalization claims but no recorded agent interface. | Current framework scope, documentation claims, licence/terms, attribution, redistribution, and limitations must be reviewed directly. |

No fourth candidate may be added until these three records are completed, rejected, or explicitly returned to `needs-review`.

## Operator sequence

Run commands from `web/` and keep incomplete drafts outside the repository.

```bash
npm run verification:draft -- google-fonts --reviewer <operator-id> --date YYYY-MM-DD --output ../verification-work/google-fonts.json
npm run verification:draft -- radix-ui --reviewer <operator-id> --date YYYY-MM-DD --output ../verification-work/radix-ui.json
npm run verification:draft -- react-aria --reviewer <operator-id> --date YYYY-MM-DD --output ../verification-work/react-aria.json
```

For each candidate, the human operator must:

1. verify the canonical destination and identity;
2. review every copied claim against current official evidence;
3. manually test every recorded agent interface when one exists;
4. review persistence, redistribution, attribution, and current terms or licence documentation;
5. review the profile limitations;
6. record complete dates, freshness, a recheck deadline, and decision notes;
7. run `npm run verification:check -- <record-path>`;
8. stop promotion when the result is invalid, stale, `needs-review`, or `rejected`.

Completed records intended for repository review will use a bounded path introduced by this slice, expected under `verification-records/1.6/`. The path and promotion consumer must be covered by repository tests before any source status changes.

## Acceptance criteria

- keep the batch fixed at three named candidates;
- create no automated provider, browser, HTTP, API, CLI, MCP, pricing, terms, licence, credential, or availability claim;
- require a genuine `human-operator` reviewer for every completed record;
- validate every completed record against `tessli.resource-verification.v1` and current canonical source/profile truth;
- reject stale fingerprints, altered claim/interface sets, impossible or misordered dates, incomplete checks, contradictory evidence, unsafe Verified decisions, and secret-bearing fields;
- define and test the reviewed repository location for completed records;
- define and test the explicit promotion consumer so record eligibility never mutates coverage implicitly;
- promote only records with `valid: true` and `eligibleForPromotion: true` after complete diff review;
- keep Listed, Profiled, and Verified coverage truthful and preserve a total of 295 sources;
- align website, public representations, MCP, catalogue, README, Product Plan v2, and build ledger with the exact promoted set;
- run focused verification tests plus formatting, TypeScript, lint, full tests, catalogue drift, build, browser, and release gates;
- retain complete operator evidence and rollback instructions without storing credentials or private provider content.

## Exclusions

- no invented human review, current availability, interface result, terms conclusion, licence conclusion, or evidence date;
- no source outside the three-candidate batch;
- no automatic promotion from a valid draft or schema-only result;
- no paid/private provider content, screenshots, downloaded assets, customer data, workspace content, cookies, tokens, passwords, API keys, or session values;
- no redesign, auth, cloud workspace, submission, moderation, analytics, email, deployment, or proof-track change;
- no change to the separate blocked Slice 5.3 human-review dependency.

## Expected files

## Privacy boundary

Operators may use their own legitimate provider credentials only in the provider's normal interface. Tessli records bounded observations, official links, dates, classifications, and notes—not secrets or private responses. Draft and validation commands remain network-free and must not inspect environment credentials.
