# Slice 10.1a — Local Supabase SSR client contract

## Goal

Introduce the local, typed Supabase client boundary required by later authentication and user-data slices without creating a cloud project, inventing database tables, or changing the public Phase 1 experience.

This slice is intentionally useful before cloud setup: client factories, environment validation, package versions, and tests can be reviewed and merged through GitHub Actions while Vercel deployments remain paused.

## Acceptance criteria

- `@supabase/ssr` and `@supabase/supabase-js` are exact pinned production dependencies.
- The application requires Node.js 22 or newer, matching repository CI and the supported Supabase JavaScript runtime.
- `.env.example` documents only the public project URL and publishable key.
- Missing or malformed public configuration fails with a named, actionable error.
- Hosted project URLs require HTTPS; localhost URLs may use HTTP for a future local Supabase stack.
- Public configuration rejects obvious secret and service-role key values.
- A browser client factory uses `createBrowserClient` with the public configuration.
- A new server client is created per request using `cookies()`, `getAll`, and `setAll`.
- No request proxy, session refresh, redirect, or authentication UI is added.
- The database type contract remains explicitly empty until the reviewed schema slice.
- Focused tests exercise environment validation and source-boundary requirements.
- Formatting, TypeScript, lint, all tests, catalogue drift, and production build pass.

## Exclusions

- no Supabase cloud project or development branch creation;
- no paid resource or cost approval;
- no real API URL, publishable key, secret key, or service-role key;
- no `proxy.ts`, middleware, session refresh, sign-in, sign-up, OTP, OAuth, or account UI;
- no database migrations, tables, views, functions, triggers, storage, or Row Level Security;
- no public catalogue duplication in Supabase;
- no cloud save, private collection, note, submission, moderation, or email work;
- no Vercel deployment or production cutover;
- no visible UI change.

## Client boundary

The local application exposes three deliberate pieces:

1. `lib/supabase/config.ts` reads and validates the two public environment variables at call time.
2. `lib/supabase/browser.ts` creates the browser client for future Client Components.
3. `lib/supabase/server.ts` creates a fresh cookie-aware server client for each Server Component, Server Action, or Route Handler request.

The server factory may receive cookie updates from Supabase. Server Components cannot always write cookies, so the factory keeps the official guarded write pattern. Slice 10.2 will add the request proxy that performs session refresh and response-cookie synchronization.

## Environment contract

```text
NEXT_PUBLIC_SUPABASE_URL
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY
```

Both values are intentionally public. A private secret or service-role key must never be stored in `NEXT_PUBLIC_` variables, browser code, fixtures, screenshots, logs, or this repository.

## Database types

`lib/supabase/database.types.ts` uses an empty generated-compatible schema shape. It must not invent `profiles`, saves, collections, or other tables before Slice 11.1 defines and reviews the database schema and RLS policies.

After a Tessli project and schema exist, replace the placeholder with generated TypeScript types from the approved project and review the generated diff.

## Cloud blocker

Cloud linking remains a separate Slice 10.1b because no Tessli Supabase project currently exists in the connected organization. Creating one requires explicit organization, region, and recurring-cost confirmation.

Slice 10.1b must record:

1. the approved organization and project;
2. region and cost confirmation;
3. project URL and publishable key placement outside Git;
4. a server and browser connectivity smoke test;
5. security and performance advisors;
6. generated types after a reviewed schema exists.
