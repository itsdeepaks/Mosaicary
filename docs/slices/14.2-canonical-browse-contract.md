# Slice 14.2 — Canonical Browse Architecture and Pagination Contract

Status: **complete contract; runtime implementation belongs to the next slice**  
Depends on: Slice 14.1 source-profile contract  
Canonical route: `/resources`

## 1. Goal

Define one shareable, paginated, progressively enhanced source browser before replacing the existing Explore and Full Reference implementations.

The canonical Browse experience must let a human or model-assisted researcher:

1. search and filter the catalogue;
2. understand why a result may fit;
3. open an internal Tessli source profile before leaving Tessli;
4. save a source from every result view;
5. share or restore the exact research state;
6. move between result pages and source profiles without losing context.

This contract supersedes the previous product split between the homepage Explore catalogue and the Full Reference catalogue.

## 2. Scope

This slice freezes:

- canonical URL parameters and normalization;
- initial filter and sort vocabulary;
- pagination rules;
- card, compact-list, and table responsibilities;
- server/client rendering boundaries;
- responsive behaviour without duplicate result trees;
- internal and external action hierarchy;
- history, focus, and scroll restoration;
- legacy route and query migration;
- loading, empty, error, and unavailable-source states;
- accessibility, performance, and browser-test requirements.

This slice changes documentation only. It does not change runtime routes, components, catalogue data, profiles, Saved storage, MCP, authentication, cloud state, or provider integrations.

## 3. Canonical route and route ownership

`/resources` is the only canonical source-browser URL.

```text
/resources
/resources?q=authentication
/resources?category=product-ui-ux
/resources?access=free,open-source&view=list&page=2
```

Rules:

- canonical metadata points to `/resources` plus normalized meaningful query state;
- the route is server-rendered from repository-managed source-profile data;
- category browsing may initially use `/resources?category=...`;
- dedicated category pages remain deferred until they provide original editorial value;
- `/resources/[slug]` is the primary destination for a source result;
- the destination provider remains a separate `Visit source` action;
- no source result is only an outbound link.

## 4. URL-state contract

### 4.1 Supported parameters

| Parameter | Cardinality | Canonical value | Default |
|---|---:|---|---|
| `q` | one | trimmed UTF-8 text, max 160 characters | empty |
| `category` | one | known category slug | all categories |
| `access` | many | comma-separated known access values in contract order | all access models |
| `type` | many | comma-separated known source-type values in contract order | all source types |
| `level` | many | comma-separated `listed`, `profiled`, `verified` | all levels |
| `sort` | one | `curated`, `name-asc`, `name-desc`, `verified-desc` | `curated` |
| `view` | one | `cards`, `list`, `table` | `cards` |
| `page` | one | positive base-10 integer | `1` |

Initial implementation does not expose capability, content-object, platform, framework, integration, freshness, or status filters. Those require a later contract because most Listed records do not carry enough intelligence for useful facets.

### 4.2 Accepted legacy input

The parser may accept:

- repeated multi-value parameters;
- comma-separated multi-value parameters;
- the old `sort=verified` alias;
- query state previously created on `/` or the old Full Reference route.

The serializer always emits the canonical representation.

Legacy `sort=verified` handling:

- map to `verified-desc` only when genuine source-profile verification dates are available;
- otherwise normalize to `curated` and remove the unsupported sort from the canonical URL;
- never map it to curated index while labeling it as verification order.

### 4.3 Normalization

- trim `q`, collapse surrounding whitespace, and cap it at 160 characters;
- ignore unknown category and enum values;
- deduplicate multi-value fields;
- serialize multi-values in schema/contract order, not interaction order;
- omit default values from the canonical query string;
- normalize invalid, zero, negative, decimal, or non-numeric `page` to `1`;
- after result derivation, clamp a direct out-of-range page to the final available page;
- an empty result set always resolves to page `1`;
- reset page to `1` when query, filter, sort, or view changes.

Examples:

```text
/resources?view=cards&page=1
→ /resources

/resources?access=open-source&access=free
→ /resources?access=free,open-source

/resources?page=-8&sort=unknown
→ /resources
```

### 4.4 History behaviour

- query typing updates history with `replaceState` or equivalent router replacement;
- committed filter, sort, view, and page actions use push navigation;
- browser Back and Forward restore the exact canonical state;
- no control keeps a second private state that can diverge from the URL;
- a copied URL produces the same result set and selected view.

The search input may debounce navigation for up to 250 ms. It must flush on Enter, blur, form submission, or route departure.

## 5. Result derivation

The order of operations is fixed:

```text
canonical source records
→ query match
→ filters
→ sort
→ total count
→ pagination
→ selected view rendering
```

Searchable Listed fields:

- name;
- domain;
- summary;
- category label;
- source type label;
- access label.

Searchable Profiled/Verified fields may additionally include:

- best-for statements;
- capabilities;
- content objects;
- platforms;
- frameworks;
- integration methods.

Limitations and evidence body text are not included in broad search during the initial implementation. They may contain long or highly specific language that creates misleading matches.

Search is token-based and case-insensitive. Every normalized query token must occur in the combined searchable text. Semantic/vector search is not part of this slice.

## 6. Sorting

### Curated

- preserves deterministic repository catalogue order;
- remains the default;
- does not imply popularity, quality, sponsorship, or trend status.

### Name A–Z / Z–A

- uses a stable locale-aware collator;
- falls back to curated index for equal names.

### Recently verified

- UI label: `Recently verified`;
- URL value: `verified-desc`;
- available only when at least one result has a truthful `profileLevel: verified` and genuine `verifiedAt` date;
- sorts dated Verified records newest first;
- stable fallback order is curated index;
- records without a qualifying date follow dated records;
- the sort control is omitted—not disabled—when no qualifying records exist.

Repository ingestion or profile status alone is not a public verification date.

## 7. Pagination

### 7.1 Page sizes

| View | Page size |
|---|---:|
| Cards | 24 |
| Compact list | 50 |
| Table | 50 |

Page size is fixed by view in the first implementation and is not a URL parameter.

### 7.2 Controls

- show Previous and Next when more than one page exists;
- show direct page links with a compact ellipsis model when useful;
- expose `aria-current="page"`;
- disable or omit impossible navigation consistently;
- announce the visible range and total count;
- changing page moves focus to the result heading unless history restoration applies;
- page links are real anchors with canonical URLs and work without JavaScript.

Recommended count copy:

```text
Showing 25–48 of 295 sources
```

### 7.3 Rendering boundary

The server derives and serializes only:

- the current page of source summaries;
- total matching count;
- page count and current page;
- facet options and counts needed by the current filter controls;
- selected canonical state.

The default page must not send all 295 full source records to the client merely to render 24 results. Static catalogue processing may happen on the server during the request/build.

## 8. View responsibilities

All views use the same canonical result set and action rules. Switching view does not change filters or sort, but resets page to `1` because page size changes.

### 8.1 Cards

Best for visual discovery and initial evaluation.

Required content:

- approved preview/fallback media;
- source name and domain;
- concise summary;
- category;
- source type;
- access model;
- profile level;
- availability state;
- internal profile link;
- Save;
- Visit source when available.

The title and preview may link to the internal profile. The whole card must not be one external anchor, and controls must not be nested inside a link.

### 8.2 Compact list

Best for scanning many sources quickly.

Required content:

- favicon/fallback mark;
- source name;
- one-line purpose;
- category or source type;
- access;
- profile level;
- internal profile link;
- Save;
- Visit source when available.

Descriptions truncate visually but remain available on the internal profile; do not hide required decision data behind hover.

### 8.3 Table

Best for dense research and comparison of catalogue facts.

Initial columns:

1. Source;
2. Source type;
3. Category;
4. Access;
5. Profile level;
6. Last verified, only for genuine Verified records;
7. Actions.

Requirements:

- semantic `<table>`, caption, column headers, and row headers where appropriate;
- no hard-coded verification date;
- no duplicate mobile and desktop table/result maps;
- below the table breakpoint, the same rows visually recompose into compact stacked rows using CSS while preserving table semantics or an equivalent single accessible rendering path;
- horizontal scrolling is a fallback, not the primary mobile design.

## 9. Result actions

### Primary action

`View Tessli profile` → `/resources/[slug]`

This remains available for active, inactive, and unknown destination status because Tessli’s local profile must not disappear when a provider is unavailable.

### Secondary actions

- `Save` uses the existing browser-local Saved contract;
- `Visit source` opens the provider in a new tab with `noopener noreferrer` only when the source is active and the URL is safe;
- unavailable or unknown destinations show status copy and do not expose a misleading active external action.

### Compare

Compare is omitted until a later slice defines defensible peer groups and the comparison surface. Do not render a disabled or universal Compare control merely because the future product may support it.

### Similar Sources

Similar Sources is primarily a Source Detail responsibility. Browse may use the same future peer/category logic for empty-state recovery, but it must not claim similarity from name or description text alone.

## 10. Filter interface

### Desktop

- persistent filter rail when available width supports it;
- query and selected-filter summary remain close to results;
- selected values are visible without reopening a menu;
- one Clear all action;
- facet counts reflect the catalogue and current supported counting rule.

### Tablet and mobile

- search remains directly available;
- filters open in a focus-managed modal sheet/dialog;
- selected-filter count appears on the trigger;
- applying or clearing filters returns focus predictably;
- Escape closes the sheet and focus returns to the trigger;
- no filter is available only on desktop.

The initial facet set is Category, Access, Source type, and Profile level. The interface may group them progressively, but it must not hide selected values.

## 11. Responsive rendering contract

Breakpoints follow `design.md` and the shared page frame.

### 1280 px and wider

- optional sticky filter rail;
- cards may use four columns when minimum width remains usable;
- list and table use the full research column;
- page controls remain within the result column.

### 768–1279 px

- two-column card grid where space permits;
- filter rail collapses to a sheet;
- compact list remains a single column;
- table begins progressive column reduction or stacked-row treatment.

### Below 768 px

- one-column cards;
- compact result rows;
- search followed by filter/sort/view controls;
- pagination uses touch-sized Previous/Next plus concise current-page context;
- no complete desktop result tree exists hidden beside a mobile result tree.

### 320 px overflow gate

- no horizontal page overflow;
- long domains and source names wrap or truncate safely;
- action groups wrap without reducing touch targets;
- table fallback remains usable.

## 12. Homepage and legacy migration

The canonical Browse implementation must not redesign the mature homepage, but it must end the competing browser model.

Migration rules:

- global `Browse`/`Resources` navigation points to `/resources`;
- query-bearing legacy Explore links preserve supported `q`, `category`, `access`, and `sort` state when moving to `/resources`;
- the old Full Reference title and product framing are removed from `/resources`;
- the existing homepage may temporarily retain a limited source preview until the later homepage phase, but it must not present itself as a second complete catalogue;
- homepage search submits to `/resources`;
- any homepage source preview uses the same canonical source summaries and internal profile action hierarchy;
- old unsupported parameters are normalized rather than echoed forever.

A limited homepage preview means no more than 12 source cards and no pagination/filter workspace. The full research task belongs to `/resources`.

## 13. Source Detail return, focus, and scroll restoration

Before navigating from Browse to a profile, store enough transient browser state to restore:

- canonical Browse URL;
- source slug or result anchor;
- scroll position;
- triggering result link where practical.

On browser Back:

- restore the same query, filters, sort, view, and page from the URL;
- restore the previous scroll/result position after content is ready;
- return focus to the source result link when focus restoration was keyboard-initiated;
- do not force restoration on a direct visit or a new forward navigation.

Implementation may use browser history state and session storage. It must not place personal research data in a public URL.

## 14. Progressive enhancement

The route remains useful without client JavaScript:

- initial requested state is server-rendered;
- search and filters are represented by a GET form or equivalent navigable links;
- pagination uses anchors;
- Source Detail and Visit source links work;
- Save may require JavaScript but its absence does not block research;
- canonical result content is not hidden behind hydration.

With JavaScript:

- controls may auto-submit or navigate without full-page reload;
- pending navigation preserves current content and marks results `aria-busy`;
- announcements describe completed result-count changes, not every keystroke.

## 15. States

### Loading/pending

- keep the previous result set visible during client navigation where practical;
- mark the result region busy;
- disable only controls that would create conflicting operations;
- use restrained progress feedback;
- do not show fake skeleton metadata or fake result counts.

### Empty

- state the active query/filter context;
- provide Clear all and targeted filter removal;
- preserve the search input;
- do not invent popular or trending recommendations;
- optional recovery links must be backed by real categories or collections.

### Error

- route-level error boundary with Retry;
- explain that the repository-managed catalogue could not be prepared;
- do not erase the user’s URL state;
- report no provider outage unless it was actually checked.

### Unavailable source

- internal profile remains navigable;
- status is visible in every view;
- external action is removed or clearly disabled without an anchor;
- unavailable records may still appear unless a future explicit status filter excludes them.

### Unknown source status

- use neutral `Status not recently confirmed` language;
- do not show a green/verified state;
- external URL may remain available only when the record itself is active under the canonical contract.

## 16. Accessibility contract

- one `<main>` and one page `<h1>`;
- logical heading order;
- labeled search and filter controls;
- visible keyboard focus;
- no nested interactive elements;
- result-count updates announced politely after navigation settles;
- filter dialog traps focus, closes on Escape, and restores trigger focus;
- view switch exposes selected state;
- pagination uses `nav` with an accessible label and `aria-current`;
- table has caption and header relationships;
- touch targets meet the repository target;
- no essential hover-only content;
- reduced-motion preference is respected;
- internal versus external destinations are clear in accessible names and visible copy.

## 17. Performance and data boundaries

- no selected view renders more than its page size;
- no mobile/desktop duplicate result map;
- no client payload includes all 295 complete intelligence profiles for Browse;
- previews below the fold lazy-load;
- source-profile enrichment remains server-side unless a field is required by the current result card;
- filtering and pagination remain deterministic and network-free against repository data;
- no vector database, external search service, Supabase catalogue copy, or new runtime dependency is required.

### Unit/contract tests

### Route/component tests

- `/resources` renders the requested page only;
- result primary links point to `/resources/[slug]`;
- external actions are separate and safe;
- Save is available in every view;
- only the selected view result tree is rendered;
- no hard-coded verification date;
- empty and error states preserve recovery actions;
- legacy query state reaches the canonical route.

### Browser widths

## 19. Implementation sequence for the next slice

1. replace Discovery state with the canonical Browse state contract;
2. create deterministic server-side result derivation and pagination;
3. create shared controls using URL navigation;
4. create card, list, and table renderers with one selected result tree;
5. make internal Source Detail links primary, even if the first profile page is a truthful minimum shell;
6. preserve existing local Save behaviour;
7. migrate global navigation and homepage search to `/resources`;
8. reduce homepage catalogue rendering to a limited compatibility preview;
9. remove Full Reference framing and hard-coded verification data;
10. add route, unit, accessibility, responsive, and history tests;
11. review the full diff and run all repository/release gates.

The Source Detail content build remains a later slice. The Browse implementation may add only the minimum truthful route shell required to avoid dead internal links, or it may coordinate a temporary non-dead profile destination explicitly documented in its PR. It must not fabricate intelligence.

## 20. Explicit exclusions

- no mature homepage redesign;
- no category-detail routes;
- no semantic/vector search;
- no recommendation ranking;
- no universal Compare;
- no new intelligence profiles merely to populate filters;
- no live provider verification;
- no authentication or cloud Saved;
- no local Boards;
- no research-pack export;
- no submission/moderation forms;
- no mass screenshot work;
- no MCP tool additions;
- no analytics or personalization;
- no new dependency unless implementation later proves a material need.

## 21. Acceptance criteria

This contract is accepted when:

- `/resources` ownership and canonical URL state are unambiguous;
- initial filters and truthful sort rules are frozen;
- card/list/table responsibilities are distinct;
- 24-card and 50-row pagination is specified;
- all-295 and duplicate responsive rendering are prohibited;
- internal profile navigation and separate provider actions are explicit;
- history, focus, and scroll restoration are specified;
- legacy Explore/Full Reference migration is bounded;
- loading, empty, error, unavailable, and no-JavaScript states are covered;
- accessibility, performance, browser, and test gates are executable;
- runtime implementation and later-product exclusions remain explicit.
