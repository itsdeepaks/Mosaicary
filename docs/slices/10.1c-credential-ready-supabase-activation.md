# Slice 10.1c — Credential-ready Supabase activation contract

## Goal

Allow Tessli development to continue before a cloud Supabase project is created, without fabricating a successful backend integration or weakening the existing secret-handling boundary.

The public application must remain fully usable when Supabase variables are absent. Later account UI may inspect configuration readiness and present a truthful unavailable state; strict client creation must still fail when code attempts to use Supabase without valid public configuration.

## Acceptance criteria

- `.env.example` documents exactly three public application variables:
  - `NEXT_PUBLIC_SITE_URL`;
  - `NEXT_PUBLIC_SUPABASE_URL`;
  - `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`.
- Supabase URL and publishable-key placeholders remain empty so copying the example does not resemble a working integration.
- No service-role, secret, private server, database password, or access-token variable is introduced.
- `readSupabasePublicConfig` remains strict and throws an actionable named error when a client is created without valid configuration.
- `inspectSupabasePublicConfig` provides a non-throwing configured/unconfigured result for auth-shell rendering.
- Hosted URLs still require HTTPS; localhost remains allowed for future local Supabase development.
- Obvious secret and service-role values remain rejected.
- Existing browser and per-request server factories remain unchanged.
- Focused tests cover configured and unconfigured readiness states and the three-variable environment example.
- Formatting, TypeScript, lint, all tests, catalogue drift, and production build pass.

## Exclusions

- no Supabase organization, cloud project, branch, database, storage bucket, or paid resource;
- no real project URL, publishable key, secret, password, or access token;
- no live browser/server connectivity claim;
- no auth route, sign-in form, session proxy, callback route, account menu, or user state;
- no database schema, migration, generated table types, or Row Level Security;
- no cloud saves, private collections, notes, forms, moderation, or email delivery;
- no public catalogue duplication in Supabase.

## Environment contract

```text
NEXT_PUBLIC_SITE_URL=https://tessli.vercel.app
NEXT_PUBLIC_SUPABASE_URL=
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=
```

Only the project URL and publishable key are needed by Tessli's browser and cookie-aware SSR clients. Supabase secret keys and service-role keys must never enter `NEXT_PUBLIC_*`, GitHub, client bundles, logs, screenshots, or fixtures.

## Deferred activation boundary

The cloud-link slice remains incomplete until a real project exists and the following checks are performed:

1. place the project URL and publishable key in local, preview, and production environment settings outside Git;
2. configure allowed site and OAuth redirect URLs;
3. run browser and server connectivity smoke tests;
4. inspect Supabase security and performance advisors;
5. configure auth providers and custom SMTP before public email testing;
6. generate database types only after the reviewed schema exists.

Until then, UI built in later credential-ready slices must show an honest unavailable state rather than fake authentication or silently failing controls.

The active delivery ledger records Slice 10.2a as the next credential-ready UI slice and keeps live auth activation in Slice 10.2b behind the deferred cloud-link checkpoint.
