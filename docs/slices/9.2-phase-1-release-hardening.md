# Slice 9.2 — Phase 1 release hardening and deployment runbook

## Goal

Turn the merged Phase 1 application into a reviewable release candidate with one permanent release gate, complete route smoke coverage, responsive browser evidence, and an explicit production-cutover and rollback boundary.

This slice does not change the production deployment target. Production replacement remains a separate externally gated slice because the active Vercel project configuration and previous known-good deployment must be readable before cutover.

## Acceptance criteria

- `build-slices.md` records Slice 9.1 as complete and separates release hardening from production replacement.
- A permanent GitHub Actions release gate runs from a locked Node.js installation.
- Formatting, TypeScript, ESLint, the complete Node test suite, catalogue drift, and the production build pass.
- Every Phase 1 route returns its expected status and truthful public content.
- All six collection detail routes return successfully.
- Unknown collection and application routes return 404.
- Browser evidence covers Explore, Collections, collection detail, Full Reference, Saved, public content, contribution guidance, and the not-found experience.
- Browser evidence is captured at 1440×900, 1280×800, 1024×768, 768×1024, 430×932, 390×844, and 360×800.
- Every browser-reviewed template has a main landmark, an `h1`, loaded fonts, a document title, and no horizontal page overflow.
- Saved evidence includes a populated browser-local state and an explicit empty v2 state.
- Browser exceptions and error-level console entries fail the gate.
- Release screenshots and logs are uploaded as one retained GitHub Actions artifact.
- The repository documents production preconditions and rollback steps without claiming an external cutover occurred.

## Exclusions

- no production-domain or Vercel project-setting change;
- no deployment promotion;
- no Supabase, authentication, analytics, cookies, email, or forms;
- no catalogue, collection, schema, or source-data change;
- no metadata scraping or preview enrichment;
- no UI redesign or unrelated visual polish;
- no dependency or lockfile change.

## Release evidence

The permanent workflow is `.github/workflows/phase-1-release-gate.yml`.

Its release artifact is named `tessli-phase-1-release-evidence` and contains:

- responsive viewport screenshots for the representative Phase 1 templates;
- a separate 390×844 Saved empty-state screenshot;
- the Chrome process log;
- the release browser-matrix log.

The workflow must pass on the exact final pull-request head before merge. The existing `Web CI` workflow remains an independent regression gate.

## Production preconditions

Production replacement is blocked until all of the following are known and recorded:

1. the accessible Vercel project ID and team owning the current Tessli deployment;
2. the current project root directory, framework preset, install command, build command, and output configuration;
3. the production domain assignments;
4. the previous known-good production deployment ID and URL;
5. a successful preview that demonstrably serves the `web/` Next.js application rather than the legacy repository-root static site;
6. an approved cutover window and smoke-test owner.

A green Vercel badge without route probes is not sufficient evidence.

## Rollback procedure

Before production replacement, record the previous known-good deployment and configuration.

If production smoke checks fail after cutover:

1. stop further configuration changes;
2. reassign or promote the previous known-good deployment to the production domain;
3. if the project root was changed, restore the previous root, framework, install, build, and output settings;
4. verify `/`, `/collections`, `/resources`, `/saved`, and `/about` on the restored production domain;
5. confirm the production domain no longer serves the failed release;
6. record the failed deployment ID, observed symptoms, rollback time, and follow-up issue before attempting another cutover.

Do not delete the previous deployment until the replacement has passed production smoke checks and remained stable through the agreed observation window.

## Security and privacy

The release gate handles no credentials or visitor data. Browser-local Saved fixtures use stable catalogue IDs inside an isolated CI browser profile. The workflow retains screenshots and logs only; browser profiles, local storage databases, environment files, and secrets are not uploaded.
