## Security decisions

`public.rls_auto_enable()` is the documented Supabase auto-RLS event-trigger
function. Inspection confirmed it is owned by `postgres`, uses
`SECURITY DEFINER`, has `search_path=pg_catalog`, and is invoked by the enabled
`ensure_rls` DDL event trigger. Direct execution was unnecessary, so execution
was revoked from `PUBLIC`, `anon`, `authenticated`, and `service_role`. The
event trigger remains enabled and the security advisor is now clear.

The only new `SECURITY DEFINER` function is `private.handle_new_user()`. It:

- lives outside the exposed `public` schema;
- has an empty search path and uses a fully qualified table name;
- inserts only the new Auth user's ID into `public.profiles`;
- has direct execution revoked from public API roles.

All eight public tables have RLS enabled. Anonymous roles receive no table
grants. Authenticated policies use `(select auth.uid())` plus the row's
`user_id`; update policies include both `USING` and `WITH CHECK`. Community
tables grant authenticated users only `SELECT` and `INSERT`, and insert policies
require `status = 'pending'`.

## Rollback

Before real user data exists, rollback may drop the eight new tables, their
private trigger functions, and their Auth trigger, then restore only the
previous empty-project state. After user data exists, rollback must use a
reviewed forward migration and backup rather than destructive table drops.
Restoring direct public execution of `rls_auto_enable()` is not part of a safe
rollback.
