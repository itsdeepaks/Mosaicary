public client boundary without creating or mutating cloud resources, activating

development server is the review surface for this checkpoint.

Tessli project:

- status: `ACTIVE_HEALTHY`;

The security advisor reported two warnings for the pre-existing

function. A dedicated security review and an explicit remediation decision are
required before schema, RLS, or live-auth work proceeds. Supabase's remediation
references are the [anonymous execution lint](https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable)
and [authenticated execution lint](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable).

The management connector's branch-listing operation failed with
`Project reference is missing when validating permissions`. This is recorded as
an unverified inventory limitation; it must not be interpreted as proof that the
project has no branches.

### Local runtime checks

The running local Tessli server at `http://localhost:3000` was inspected in the
Codex in-app browser:

- `/auth` rendered the configured shell at 1440px and 390px;
- the page reported `data-auth-configuration="configured"`;
- both viewports had no horizontal overflow;
- the two auth controls remained disabled and no sign-in request was submitted;
- the browser console had no error or warning entries for the check.

A temporary, non-committed Node harness invoked the actual Tessli factories in
`web/lib/supabase/browser.ts` and `web/lib/supabase/server.ts` using the ignored
local values. The two factory constructions and unauthenticated reads were
performed independently:

- browser factory: client created; no session; `getUser()` returned the expected
  `AuthSessionMissingError` for an unauthenticated browser;
- server factory: client created with a request cookie adapter; no session;
  `getUser()` returned the same expected unauthenticated result.

The unauthenticated `getUser()` result is a factory smoke and is not presented
as proof that the call reached the network. The separate Auth settings request
below is the endpoint-reachability evidence.

A read-only `GET /auth/v1/settings` request using the public key returned HTTP
200. The observed provider state was signup enabled, email enabled, Google
disabled, and phone disabled. This confirms the endpoint is reachable; it does
not activate or approve any authentication method.
