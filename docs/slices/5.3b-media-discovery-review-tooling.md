# Slice 5.3b — Media discovery and review tooling

Status: **active on `codex/media-discovery-review-tooling`**  
Base commit: `b42e645552cf3321bcc2c8eaf0b2c2d0cf044003`

## Goal

Create a safe, explicit, repeatable workflow for discovering, recording, reviewing, and refreshing website-card image metadata without allowing unreviewed candidates to enrich Tessli's production catalogue.

The approved production source remains `lib_data/resource-media.json`. Discovery candidates remain separate and require manual reviewer approval before any record may be copied into that source.

## Acceptance criteria

1. A versioned JSON Schema defines candidate/review records separately from approved production media.
2. Candidate records include the Tessli resource ID, resource name, canonical destination, source page, checked date, reviewer status, and explicit discovery outcome.
3. A successful preview candidate records HTTPS raster URL, `manual` or `open-graph` source, and declared/verified raster content type.
4. A successful favicon candidate records HTTPS raster URL and content type.
5. Failures, redirects, blocked pages, non-HTML pages, SVG-only results, unsafe destinations, and uncertain results are represented explicitly rather than silently omitted.
6. Candidate validation rejects unknown resources, duplicate resource entries, URL credentials, literal IP hosts, localhost/private-style hosts, non-HTTPS URLs, unsupported ports, excessive URL lengths, unsupported content types, remote SVGs, invalid dates, mismatched resource names/destinations, and invalid reviewer transitions.
7. A deterministic review script reads only repository files, validates candidates, compares them with approved media, and writes a stable JSON/Markdown report.
8. The normal catalogue generator, test suite, and build do not fetch external websites and do not read candidate records as approved media.
9. Tests prove that malformed or review-pending candidates cannot enrich `web/data/catalogue.json`.
10. An explicit, opt-in discovery command may fetch only selected resources; it is never invoked by normal build/test/CI.
11. Network discovery validates every source/redirect/media destination, rejects unsafe hosts and protocols, applies redirect/time/HTML-size limits, accepts only HTTPS public-hosted raster media, and emits review-pending candidates rather than modifying approved records.
12. Discovery order and report serialization are deterministic for the same inputs.
13. Initial review coverage targets a small asset/design-resource shortlist; no attempt is made to approve all 295 resources.
14. Contributor documentation explains discovery, review, approval, refresh, rejection, and blocked-site workflows.
15. Existing card fallback remains manual preview → Open Graph preview → favicon → generated mark.
16. Existing browser interaction and responsive checks pass at 1440, 1024, 768, and 390px with no horizontal overflow.
17. `build-slices.md` records 5.3a as `DONE` and 5.3b as `DONE` only after this slice passes review and CI.

## Exclusions

- no mass enrichment of all 295 resources;
- no automatic publication of discovered candidates;
- no third-party image binaries downloaded or committed;
- no screenshot capture or scraper;
- no unrestricted image proxy, wildcard `next/image` configuration, or first-party cache;
- no remote SVG approval or rendering;
- no network call during normal catalogue generation, tests, build, or CI;
- no changes to card visual design, search UI, auth, Supabase, intelligence profiles, collections, or catalogue descriptions;
- no invented image URL, MIME type, licensing claim, price, access model, or product metadata;
- no later media-cache or broad-coverage slice.

## Security boundary

The approved sidecar is publication truth. Candidate data is research evidence only.

An opt-in discovery run must:

- accept only selected catalogue resource IDs;
- fetch only HTTPS URLs without credentials;
- reject literal IP addresses and unsafe hostnames;
- resolve hostnames and reject private, loopback, link-local, multicast, unspecified, and metadata-service addresses;
- follow redirects manually and revalidate every destination;
- limit redirects, response time, HTML bytes, and URL length;
- require HTML for source pages;
- accept only JPEG, PNG, WebP, or AVIF media responses;
- cancel image bodies after headers are validated;
- never persist a candidate as approved;
- record blocked and uncertain outcomes truthfully.
